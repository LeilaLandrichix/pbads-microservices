1. Project Overview

PBADS is a full-stack microservices system designed to analyze personal habit data (sleep, diet, activity, mood) and detect behavioral anomalies in real-time. The system uses machine learning algorithms to identify patterns and deviations from normal behavior, providing users with timely alerts, AI-powered recommendations, and insights.

The system follows a 13-service microservices architecture with clear separation of concerns, enabling scalability, maintainability, and fault tolerance. It combines synchronous HTTP communication for immediate responses with asynchronous Kafka messaging for event-driven processing. The system integrates Google Gemini AI for generating personalized recommendations based on detected anomalies.

2. Architecture & Workflow

2.1 System Architecture Layers

The PBADS architecture is organized into four main layers:

🌐 Frontend Layer

Frontend Service (Port 3000) - Thymeleaf-based web application providing user interface for:

  • User authentication and registration
  • Daily habit data entry
  • Dashboard with statistics and charts
  • Alert viewing and management
  • User management (Admin only)

🚪 API Gateway Layer

API Gateway (Port 8080) - Spring Cloud Gateway serving as:

  • Single entry point for all client requests
  • Request routing to appropriate microservices
  • Authentication and authorization
  • Rate limiting and circuit breaking
  • CORS handling

🏗️ Infrastructure Layer

  • Eureka Server (Port 8761) - Service discovery and registry
  • Config Server (Port 8888) - Centralized configuration management
  • Kafka - Asynchronous message broker for event-driven communication
  • PostgreSQL - Relational databases (one per service for data isolation)
  • Redis - Caching and session management
  • MLflow (Port 5000) - ML experiment tracking and model versioning

⚙️ Core Services Layer

  • Auth Service (Port 8081) - Authentication, authorization, and user management
  • Data Service (Port 8082) - Habit data CRUD operations
  • Model Service (Port 8083) - ML model training and management
  • Inference Service (Port 8084) - Real-time anomaly detection
  • Alert Service (Port 8085) - Alert generation and notification management
  • Monitoring Service (Port 8086) - Observability with Prometheus/Grafana
  • Recommendation Service (Port 8087) - AI-powered recommendations using Google Gemini

2.2 Complete Workflow

The system follows this workflow when processing user data:

Step 1: User Authentication
User logs in through Frontend Service → Frontend calls Auth Service via Gateway → Auth Service validates credentials → Returns JWT token → Frontend stores token in session
Step 2: Data Entry
User submits daily habit data (sleep, steps, calories, water, study hours, mood) → Frontend Service sends POST request to Data Service via Gateway → Data Service validates and persists data in PostgreSQL
Step 3: Event Publishing (Dual Mode)
Data Service publishes DataLoggedEvent to Kafka topic data.logged.events AND makes direct HTTP call to Inference Service (fallback mechanism)
Step 4: Anomaly Detection
Inference Service receives event (via Kafka consumer or HTTP endpoint) → Loads ML model from Model Service or cache → Prepares feature vector → Runs anomaly detection algorithm → Calculates anomaly score (0-1) → Determines anomaly level (NORMAL/LOW/MEDIUM/HIGH)
Step 5: AI Recommendation Generation (If Anomaly Detected)
Inference Service detects anomaly → Builds data summary with anomaly details and user habits → Calls Recommendation Service via HTTP → Recommendation Service sends prompt to Google Gemini AI → Gemini generates personalized recommendations → Recommendation Service returns recommendation to Inference Service
Step 6: Alert Generation with Recommendation
Inference Service creates AnomalyDetectedEvent with recommendation → Publishes to Kafka topic anomaly.detected.events AND makes direct HTTP call to Alert Service with recommendation → Alert Service persists alert with AI recommendation in database
Step 7: User Notification
Alert Service stores alert with recommendation → Frontend Service polls Alert Service every 5 seconds for new alerts → Push notification (toast) appears in dashboard when new alert detected → Dashboard displays alerts with severity levels → User can view recommendations and acknowledge/resolve alerts

4. Machine Learning Model

4.1 Model Training Process

The PBADS system uses unsupervised anomaly detection algorithms to identify deviations from normal behavior patterns. The model is trained on historical habit data without requiring labeled anomaly examples.

Training Pipeline

  1. Data Loading: Reads CSV file containing historical daily habit data
  2. Feature Extraction: Extracts 7 features:
    • Sleep_Hours
    • Steps
    • Calories_Burned
    • Water_Intake_ml
    • Study_Hours
    • Mood_Score
    • Wake_Up_Time_Hours (converted from time format)
  3. Data Preprocessing:
    • Handles missing values
    • Removes infinite values
    • Standard scaling (StandardScaler) - normalizes features to mean=0, std=1
  4. Model Training: Trains selected algorithm on preprocessed data
  5. Model Evaluation: Calculates metrics (anomaly rate, score distribution)
  6. Model Persistence: Saves model (.joblib) and metadata (.json) to disk

4.2 Algorithms Used

🌲 Isolation Forest (Primary Algorithm)

Why Isolation Forest?

  • Excellent for high-dimensional data
  • Fast training and inference
  • Works well with mixed data types
  • No need for labeled anomaly data
  • Handles outliers effectively

How It Works:

Isolation Forest builds an ensemble of isolation trees. Each tree randomly selects a feature and randomly selects a split value. Anomalies are points that require fewer splits to isolate, meaning they are easier to separate from the rest of the data.

Hyperparameters:

  • contamination: Expected proportion of anomalies (default: 0.1 = 10%)
  • n_estimators: Number of trees in the forest (default: 100)
  • random_state: Seed for reproducibility (42)

Output: Anomaly score normalized to 0-1 scale (higher = more anomalous)

🔷 One-Class SVM (Alternative Algorithm)

Why One-Class SVM?

  • Good for non-linear anomaly detection
  • Effective with RBF kernel for complex patterns
  • Robust to outliers
  • Alternative when Isolation Forest doesn't perform well

How It Works:

One-Class SVM learns a decision boundary that encompasses normal data points. Points outside this boundary are considered anomalies. Uses RBF (Radial Basis Function) kernel to handle non-linear patterns.

Hyperparameters:

  • nu: Upper bound on fraction of outliers (default: 0.1)
  • gamma: RBF kernel coefficient (default: 'scale')
  • kernel: Kernel type (default: 'rbf')

Output: Decision function score converted to 0-1 scale using sigmoid transformation

4.3 Model Inference

During inference, the trained model receives a feature vector representing a single day's habits. The model outputs an anomaly score (0-1), which is then interpreted as:

Anomaly Score Level Interpretation
0.0 - 0.3 NORMAL Behavior is within normal range
0.3 - 0.6 LOW Minor deviation from normal
0.6 - 0.8 MEDIUM Moderate anomaly detected
0.8 - 1.0 HIGH Significant anomaly requiring attention

4.4 Rule-Based Fallback

When the ML model is unavailable, the system falls back to rule-based detection using predefined thresholds:

  • Sleep Hours: Normal range 6-10 hours
  • Steps: Minimum 5000 steps per day
  • Water Intake: Minimum 1500ml per day
  • Mood Score: Minimum 3 out of 10
  • Study Hours: Maximum 12 hours per day

5. Service Communication

5.1 Synchronous Communication (HTTP/REST)

Synchronous communication is used for operations requiring immediate responses, such as user authentication, data retrieval, and direct service calls.

  • Protocol: HTTP/REST
  • Client: Spring Cloud OpenFeign
  • Gateway: Spring Cloud Gateway (Port 8080)
  • Service Discovery: Eureka Server

Communication Patterns:

  • Frontend → Gateway → Auth Service: Login, registration, user management
  • Frontend → Gateway → Data Service: Data entry, data retrieval
  • Frontend → Gateway → Alert Service: Alert fetching (polling every 5 seconds)
  • Frontend → Gateway → Recommendation Service: Dashboard recommendations
  • Data Service → Inference Service: Direct HTTP fallback when Kafka unavailable
  • Inference Service → Recommendation Service: AI recommendation generation
  • Inference Service → Alert Service: Direct HTTP alert creation with recommendations
  • Inference Service → Model Service: Model loading

5.2 Asynchronous Communication (Kafka)

Kafka is used for event-driven communication, enabling decoupling and scalability. Services publish events without waiting for consumers, allowing for better fault tolerance.

Kafka Topics:

Topic Name Publisher Consumer Event Type Description
data.logged.events Data Service Inference Service DataLoggedEvent Published when user submits daily habit data. Contains: userId, date, sleepHours, steps, caloriesBurned, waterIntakeMl, studyHours, moodScore, wakeUpTime
anomaly.detected.events Inference Service Alert Service AnomalyDetectedEvent Published when anomaly is detected. Contains: userId, date, anomalyScore, anomalyLevel, message, contributingFactors, recommendation (AI-generated)

Event Structure Details:

DataLoggedEvent

  • userId (String) - User identifier
  • date (LocalDate) - Date of the data entry
  • sleepHours (Double) - Hours of sleep
  • steps (Integer) - Number of steps
  • caloriesBurned (Integer) - Calories burned
  • waterIntakeMl (Integer) - Water intake in milliliters
  • studyHours (Double) - Hours of study
  • moodScore (Integer) - Mood score (1-10)
  • wakeUpTime (LocalTime) - Wake up time

AnomalyDetectedEvent

  • userId (String) - User identifier
  • date (String) - Date of anomaly
  • anomalyScore (Double) - Anomaly score (0.0-1.0)
  • anomalyLevel (String) - Severity level (NORMAL/LOW/MEDIUM/HIGH)
  • message (String) - Human-readable message
  • contributingFactors (Map<String, Object>) - Factors contributing to anomaly
  • recommendation (String) - AI-generated recommendation from Gemini (optional)

Complete Event Flow:

  1. Data Service publishes DataLoggedEvent to Kafka topic data.logged.events AND makes direct HTTP call to Inference Service (dual mode)
  2. Inference Service consumes the event (via Kafka consumer OR HTTP endpoint) and performs anomaly detection
  3. If anomaly detected:
    • Inference Service builds data summary with anomaly details and user habits
    • Inference Service calls Recommendation Service via HTTP with data summary
    • Recommendation Service sends prompt to Google Gemini AI API
    • Gemini AI generates personalized recommendations
    • Recommendation Service returns recommendation to Inference Service
    • Inference Service publishes AnomalyDetectedEvent to Kafka topic anomaly.detected.events AND makes direct HTTP call to Alert Service with recommendation
    • Alert Service consumes the anomaly event (via Kafka consumer OR HTTP endpoint) and creates an alert with recommendation
  4. Frontend Service polls Alert Service every 5 seconds for new alerts
  5. When new alert detected, Frontend displays push notification (toast) to user
  6. User can view alerts and recommendations on dashboard and alerts page

5.3 Fallback Mechanism

The system implements a dual-mode communication strategy for reliability:

  • Primary: Kafka for asynchronous event processing
  • Fallback: Direct HTTP calls when Kafka is unavailable

This ensures the system continues to function even if Kafka is down, though with reduced decoupling. The Data Service and Inference Service both attempt Kafka publishing but also make direct HTTP calls as a failsafe.

5.4 Resilience4j Integration

The Frontend Service uses Resilience4j for fault tolerance when calling backend services:

  • Circuit Breaker: Prevents cascading failures by opening circuit after 50% failure rate
  • Retry: Automatically retries failed requests (max 3 attempts, 1s delay)
  • Fallback: Graceful degradation when services are unavailable

Configuration:

  • Sliding window size: 10 calls
  • Failure rate threshold: 50%
  • Wait duration in open state: 10 seconds
  • Retry max attempts: 3
  • Retry wait duration: 1000ms

8. Key Design Decisions

8.1 Microservices Architecture

Why microservices? Enables independent scaling, technology diversity, fault isolation, and team autonomy. Each service can be developed, deployed, and scaled independently.

8.2 Database per Service

Why separate databases? Ensures data isolation, allows independent schema evolution, prevents tight coupling, and enables service-specific database optimizations.

8.3 Dual Communication Mode

Why Kafka + HTTP fallback? Kafka provides decoupling and scalability for event-driven architecture, while HTTP fallback ensures system continues functioning if Kafka is unavailable. This hybrid approach balances reliability with architectural benefits.

8.4 Unsupervised Anomaly Detection

Why unsupervised learning? No need for labeled anomaly data, which is difficult to obtain. Isolation Forest and One-Class SVM can learn normal patterns and identify deviations automatically.

8.5 Resilience4j Integration

Why Resilience4j? Provides circuit breakers and retries to prevent cascading failures. When a service is down, the circuit opens, preventing wasted resources and enabling graceful degradation.

8.6 AI-Powered Recommendations

Why Google Gemini AI? Provides natural language understanding and generation capabilities for creating personalized, contextual recommendations. When an anomaly is detected, the system automatically generates actionable advice tailored to the specific user's situation and detected issues.

8.7 Push Notifications

Why polling-based notifications? Simple and reliable approach that works without WebSocket complexity. Frontend polls Alert Service every 5 seconds, and when a new alert is detected, displays an ephemeral toast notification. This ensures users are immediately informed of new anomalies.

8.8 Dashboard Filtering

Why client-side filtering? Provides instant, responsive filtering without server round-trips. Chart.js's update() method allows smooth transitions between filtered views (Week, Month, Year, All), enhancing user experience while reducing server load.
